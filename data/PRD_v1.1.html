1 五点技术要求落地

要求1：架构稳定、可扩展性强

分层架构 + 接口抽象
  • 表现层：Web前端（React/Vue），只通过API网关与后端通信
  • 业务层：FastAPI，负责会话、问答编排、公文生成、流程导引
  • 能力层（核心抽象）：
    • LLMProvider 接口：chat() / embed()，实现 CloudLLM 和 OllamaLLM 两个类
    • VectorStore 接口：add() / search()，实现 ChromaStore，预留 MilvusStore
    • DocumentParser 接口：预留PDF/Word解析扩展
  • 数据层：PostgreSQL + 向量库，通过Repository模式访问
# 切换私有化只需改环境变量
LLM_PROVIDER=cloud        # cloud → ollama
EMBED_PROVIDER=cloud      # cloud → bge_local
VECTOR_STORE=chroma       # chroma → milvus
DB_URL=postgresql://...   # 同一套schema

要求2：自动化部署与优化

Docker Compose 一键启动
  • 四个服务：frontend + backend + postgres + chroma
  • 提供 init.sql 自动建表，seed.py 自动导入政策/办事/模板数据
  • 环境变量统一放 .env，提供 .env.example
  • 云端：服务器 docker compose up -d 即可；私有化：同样命令搬到内网

要求3：数据库稳定可扩展

PostgreSQL + 规范表结构
  • 用 PostgreSQL（非SQLite），生产可用、易扩展、私有化直接复用
  • 核心表：conversations、messages、documents、document_chunks、service_guides、doc_templates、audit_logs
  • 所有表带 created_at / updated_at；消息表预留 tokens、latency_ms、source_ids 字段用于评测
  • 索引：会话按 user_id+updated_at，分块按 doc_id

要求4：RAG 高质量设计

检索链路（验收指标导向）
  1. 语义切片：政策文档按"条款/段落"切，不硬切固定长度；chunk 300-500字，overlap 50字
  2. Embedding：中文向量模型，每个chunk存原文+元数据（doc_id/title/条款号）
  3. 检索 Top-K=5：向量召回
  4. Rerank（必做）：用LLM或规则对Top-5重排，把最相关的前置（直接提升MRR和引用准确率）
  5. Prompt约束：
    • "只能基于以下材料回答，不允许编造"
    • "每个事实后用[n]标注引用来源"
    • "材料不足时回答'暂未找到相关政策信息，建议咨询相关科室'"
  6. 引用溯源：返回 sources[]，含文件名、文号、条款定位，前端渲染

要求5：对标验收指标，持续整改

建立"测试→评测→整改"闭环。Day3交付前，我（小赵）按UAT测试集逐项验收，不达标项进整改清单。
